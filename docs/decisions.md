## Resolved items

| # | Step | Item | Decision |
|---|---|---|---|
| A1 | 1.0 | Cortex version (spec says 3.x) | **Cortex 4.1.0 with Elasticsearch 8.19.21**, approved by the integrator. Cortex 3.2.1 (last 3.x) only supports Elasticsearch 7.x, which is end of life; Cortex 4.0+ supports only ES 8. This matches StrangeBee's current reference pairing (TheHive 5.7.6 + Cortex 4.1.0). TheHive 5.8.0 exists but is not yet in the reference, so 5.7.6 is used. Verified against the Cortex 4.1.0 source: the Docker job runner is still supported (default runners `[kubernetes, docker, process]`), and the image's entrypoint maps the env vars `job_directory` / `docker_job_directory` to `job.directory` / `job.dockerDirectory`. Recorded as D27 in PROJECT.md. |
| A2 | 1.0 | MISP layout | Current `misp-docker` serves HTTPS from a separate `misp-nginx` container (port 8443) in front of `misp-core`. The intel node therefore also runs `misp-nginx`, and `MISP_URL` points to it (`https://misp-nginx:8443` in single-host mode, `https://<INTEL_HOST>:9443` in distributed mode). Adds ~0.1 GB; section 8's table and D28 in PROJECT.md updated. |
| A3 | 1.0 | Container memory limits | `mem_limit` values equal the RAM estimates in section 8 (e.g. `grafana` 200m / 100m). They are tuned in step 1.7 from the `mem-report.sh` measurements. |
| A4 | 1.0 | How `.env` files are produced | `render-env.sh` renders `nodes/<node>/.env` from `.env.example` + `topology.env`. In `.env.example`, `__secret__` means "generate a random secret once and keep it", `__bootstrap__` means "filled by `bootstrap.sh`, then kept". Topology-derived keys are recomputed every run; everything else (image tags) is copied from `.env.example`, so a version bump reaches existing machines with a re-render. Unknown keys in an existing `.env` are kept with a warning. `.env` is written with mode 600. |
| A5 | 1.0 | Secret format | 32 characters: letters (upper and lower), digits and one `-`. Satisfies the Wazuh password policy and needs no quoting in `.env`, YAML or URLs. |
| A6 | 1.0 | Lab node configuration | `nodes/lab/.env.example` added (not in section 12's tree): the lab node needs its own `SOC_INSTANCE`, `WAZUH_MANAGER_ADDR` and memory limit to be runnable on its own. |
| A7 | 1.0 | Mode vs node names in `soc.sh` | Arguments are run modes (section 8.1) or node names. `core` is both; it means the mode (core + lab). `cases` is the same either way; `intel` and `lab` are node names. |
| A8 | 1.0 | Non-interactive reset | `soc.sh reset <nodes> --yes` skips the confirmation prompt, for the backup round trip (step 1.8) and the fresh-clone test (step 1.9). |
| A9 | 1.0 | Extra scripts | `scripts/lib/common.sh` (shared helpers) and `scripts/ci-checks.sh` (the CI checks of section 11.5, run the same way locally and in GitHub Actions through pinned Docker images, on a snapshot of the non-ignored files so local secrets are never scanned). Neither is in section 12's tree; both are integrator-owned. |
| A10 | 1.0 | `preflight.sh` thresholds | RAM: >= 9 GiB for `standard`, >= 5.5 GiB for `low` (what WSL reports for `memory=10GB` / `6GB`). Disk: fail below 20 GiB free, warn below 60 GiB. A required port counts as free if a container of this `SOC_INSTANCE` already holds it, so `init` stays idempotent. |
| A11 | 1.0 | `WAZUH_INDEXER_URL` | Always `https://wazuh-indexer:9200`: the indexer is internal to `core` and never published (section 3.1). |
| A12 | 1.0 | Startup | `soc.sh init` / `up` use `docker compose up --wait` (timeout 900 s, override with `SOC_UP_TIMEOUT`), so bootstrap only runs once services are healthy. Nodes with no services yet are skipped. Helper scripts added in later steps (`gen-certs.sh`, `bootstrap.sh`, `healthcheck.sh`) are skipped with a `SKIP` line until they exist. |
| A13 | 1.0 | Windows 10 fallback | `netsh portproxy` forwards TCP only, so syslog on 514/udp isn't reachable from the LAN on Windows 10 machines; use syslog over TCP there, or Windows 11 mirrored networking. |
| A14 | 1.0 | `soc.sh info` credential variables | UI logins are read from these `.env` keys, which later steps must use: `GRAFANA_ADMIN_USER`/`_PASSWORD`, `N8N_OWNER_EMAIL`/`N8N_OWNER_PASSWORD`, `WAZUH_API_ADMIN_USER`/`_PASSWORD`, `THEHIVE_ADMIN_USER`/`_PASSWORD`, `CORTEX_ADMIN_USER`/`_PASSWORD`, `MISP_ADMIN_EMAIL`/`MISP_ADMIN_PASSWORD`. |
| A15 | 1.1 | Indexer certificate name | The official certificate tool only accepts dotted DNS names, so the indexer certificate is issued for `wazuh.indexer` (CN `wazuh-indexer`) and the `wazuh-indexer` service carries the network alias `wazuh.indexer`, as in `wazuh-docker`. `WAZUH_INDEXER_URL` is therefore `https://wazuh.indexer:9200`; clients that verify the certificate (Filebeat, Grafana in C8) must use that name. |
| A16 | 1.1 | Indexer admin password | `gen-certs.sh` also writes `nodes/core/certs/internal_users.yml` (git-ignored) with the bcrypt hash of `INDEXER_ADMIN_PASSWORD`, hashed with the indexer image's own tool. It contains only `admin` (the demo users are dropped) and is loaded into the security index on the first start only; changing the password afterwards needs `securityadmin.sh` (or `soc.sh reset core`). The certificate tool itself is downloaded from `packages.wazuh.com` by the generator image at generation time (D6). |
| A17 | 1.1 | Wazuh API administrator | `wazuh-wui` with a generated password (`WAZUH_API_ADMIN_USER` / `_PASSWORD`), set by the manager image, which disables the other default user (`wazuh`/`wazuh`). Verified: the default credentials are rejected. |
| A18 | 1.1 | `n8n-api` read-only role (C2) | Role `n8n-api-readonly` linked to Wazuh's built-in read-only policies: `agents_read_agents`, `agents_read_groups`, `rules_read_rules`, `decoders_read_decoders`, `lists_read_rules`, `mitre_read_mitre`, `syscheck_read_syscheck`, `syscollector_read_syscollector`, `sca_read_sca`, `rootcheck_read_rootcheck`, `ciscat_read_ciscat`, `cluster_read_resourceless`. Wazuh rejects custom policies identical to built-in ones, so none are created. Verified: listing agents and rules works; active response, manager restart and user creation return 403. "Alerts" are not a Wazuh API resource (they live in the indexer). |
| A19 | 1.1 | `grafana-ro` indexer role (C8) | Role `asox_grafana_ro`: cluster `cluster_composite_ops_ro`; on `wazuh-alerts-*` only: `read`, `indices:admin/mappings/get`, `indices:admin/resolve/index`. Created (or updated) through the security REST API by `bootstrap.sh`. Verified: it can count alerts and gets 403 on other indices. |
| A20 | 1.1 | Syslog exposure | The syslog listener (514/udp) accepts any source (`allowed-ips 0.0.0.0/0`). Acceptable in the lab since single-host mode binds to `127.0.0.1`; restricting it is Wazuh-owner backlog before exposing `core` on a LAN (PROJECT.md 11.3). Agent enrollment, originally open too, now requires a password (A25). |
| A21 | 1.1 | How Wazuh config reaches the manager | `ossec.conf`, `rules/` and `decoders/` are mounted under `/wazuh-config-mount`, which the image copies into `/var/ossec` at every start: edit, then restart the manager. Deleting a file from the repo does not delete the copy already in the `wazuh_etc` volume. |
| A22 | 1.1 | `wazuh-query.sh` access | Runs `curl` inside the `wazuh-indexer` container (the indexer is not published) as the read-only `grafana-ro` user. Exit code 0 when alerts match, 1 when none, 2 on errors, so other scripts can use it. |
| A23 | 1.1 | Test rule | Rule `100100`, level 10 (above the C1 threshold of 7), matches the marker `ASOX_TEST_EVENT` in any event. Besides the lab agent (step 1.2), it can be fired through syslog: `echo "<13>$(date '+%b %e %T') host asox-test: ASOX_TEST_EVENT id=x" \| nc -u -w1 127.0.0.1 514`. |
| A24 | 1.1 | Indexer healthcheck | Uses the admin client certificate instead of a password, so no credentials are in the indexer's environment (and no false positive in the secret scan). |
| A25 | post-1.1 | Agent enrollment password (D33) | `WAZUH_ENROLLMENT_PASSWORD` is a `__secret__` in `nodes/core/.env.example`, so `render-env.sh` generates it once per machine. `ossec.conf` sets `<use_password>yes</use_password>`, and `config/entrypoint-scripts/10-enrollment-password.sh` (run by the manager image before Wazuh starts) writes it to `/var/ossec/etc/authd.pass` (root:wazuh 640) at every start, so the file always matches `.env` and no password file is stored on disk outside the container. If the variable is empty the file is removed and authd generates a random password, so enrollment fails closed; compose also refuses to start without it. Verified on port 1515: no password and a wrong password are refused, the right one enrolls. The lab agent (step 1.2) gets the same value from `nodes/core/.env` through `render-env.sh`; an agent on another machine needs it copied. |
| A26 | post-1.1 | Restarting the manager container | Two upstream `wazuh-docker` 4.14 issues broke `docker restart` (and any Docker/WSL reboot, since the container is restarted, not recreated). (1) The image's init deletes its data template after the first start; on a restart it finds the `multigroups` volume empty (no agent groups), fails, logs `0-wazuh-init: exited 1` and skips its remaining steps, including the config copy of A21, so edited rules were silently not applied. A placeholder file doesn't help: Wazuh removes it. (2) A manager stopped mid-start leaves a stale `start-script-lock` directory, and the next start refuses to run. `config/entrypoint-scripts/05-restart-fixes.sh` repeats the skipped steps with upstream's own commands (copy `/wazuh-config-mount`, fix ownership of `queue/rids` and `etc/lists`) and removes the stale lock. The `0-wazuh-init: exited 1` log line on restarts is therefore expected and harmless. Verified: 5 consecutive restarts healthy (~20 s each, peak ~370 MiB, no OOM kill), and a rule added, then removed, is applied on a plain restart. `soc.sh down` / `up` recreate the container and were never affected. |
| A27 | post-1.1 | Manager healthcheck | Healthy only when the API answers **and** `wazuh-analysisd`, `wazuh-remoted`, `wazuh-authd`, `wazuh-db`, `wazuh-modulesd` and `wazuh-apid` are running. Previously the API alone counted, so the container reported healthy while the rest was still starting. |
| A28 | 1.2 | Lab agent image | Built locally from `nodes/lab/Dockerfile`: pinned `LAB_BASE_IMAGE` (Ubuntu 24.04, dated tag) plus `wazuh-agent=${WAZUH_AGENT_VERSION}-1` from the official Wazuh apt repository, tagged `asox-lab-agent:<version>` (never `latest`). `soc.sh init` builds it; the first build needs `packages.wazuh.com` (D6). |
| A29 | 1.2 | Lab agent configuration | `entrypoint.sh` renders `ossec.conf` at every start from the package's default configuration with only the changes a real endpoint needs: the manager address (`WAZUH_MANAGER_ADDR`) and automatic enrollment (`<enrollment>` with `agent_name` and the enrollment password in `etc/authd.pass`). The lab adds one monitored file, `/var/log/asox-lab/test.log` (syslog format), for `trigger.sh`. The default modules (SCA, rootcheck, FIM, syscollector) stay on, so the agent also produces realistic alerts for Grafana. Agent name: `LAB_AGENT_NAME` (default `lab-agent`). |
| A30 | 1.2 | Lab agent enrollment state and re-enrollment | `/var/ossec/etc` (with `client.keys`) is a named volume, so the agent enrolls once and survives restarts and `soc.sh down`/`up`. A fresh agent is refused while the manager still has an agent with the same name ("Duplicate agent name"), as with real endpoints. So `soc.sh reset lab` (without core) first removes the agent's registration through the Wazuh API when core runs on the same machine, and otherwise prints the `manage_agents -r` command to run on the core machine. Resetting core resets lab too (mode `core`), so both start clean. The Wazuh API helpers moved to `scripts/lib/wazuh.sh`, shared by `bootstrap.sh` and `soc.sh`. |
| A31 | 1.2 | Lab agent healthcheck | `nodes/lab/healthcheck.sh`: healthy when the agent is connected, has received the manager's shared configuration (`merged.mg`), and its log collector started after that. After enrolling, the agent reloads when the shared configuration arrives (~20 s after connecting), and lines written to the test log before the collector restarts are never read. With a "connected" check alone, the first trigger right after `init` was lost. |
| A32 | 1.2 | Values shared between nodes | New `.env.example` marker `__from:<node>__`: `render-env.sh` copies the key from `nodes/<node>/.env` when that file exists on the machine (nodes are rendered core first), otherwise keeps the current value (pasted by hand in distributed mode) and warns while it is empty. Used for the lab's `WAZUH_ENROLLMENT_PASSWORD`; planned for n8n's TheHive and Cortex API keys (step 1.7). |
| A33 | 1.2 | `trigger.sh` interface | `nodes/lab/trigger.sh [--id ID]` appends `ASOX_TEST_EVENT id=<ID>` to the lab agent's test log and prints the ID on stdout (messages on stderr), so callers can capture it and search for the alert: `id=$(nodes/lab/trigger.sh) && scripts/wazuh-query.sh --rule 100100 --match "$id"`. It doesn't wait for the alert itself, so the lab node references nothing outside its folder (section 12). |
| A34 | 1.3 | Grafana version and memory | Grafana 13.2.2 grew by ~100 MiB of retained Go heap per browser session (live heap 74 → 276 → 361 → 402 → 435 → 532 MiB over five headless sessions of login + dashboard, never released), so it hit its 200 MB limit and restarted twice. It is not caused by our queries: the same panel queries through the API alone kept the heap flat. 12.4.11 under the identical test stays at ~56 MiB live / ~175 MiB total, so it is pinned instead (PROJECT.md D34). Limits: `GRAFANA_MEM` 256m (standard) / 192m (low), up from 200m / 100m; a clean 12.4 idles at ~155 MiB. Re-test before moving to 13.x. |
| A35 | 1.3 | Grafana plugin installation | Only the pinned `grafana-opensearch-datasource` 2.34.4, through the image's `GF_INSTALL_PLUGINS` (deprecated but still supported; it only runs with `GF_INSTALL_PLUGINS_FORCE=true`), with `GF_PLUGINS_PREINSTALL_DISABLED=true`. The newer `GF_PLUGINS_PREINSTALL[_SYNC]` always adds Grafana's default app plugins (drilldown apps, advisor) at unpinned versions and auto-updates bundled datasources from the internet at every start; disabling preinstall also disables `_SYNC`, so it can't be used for the pinned plugin. |
| A36 | 1.3 | Datasource settings (C8) | Provisioned from `provisioning/datasources/wazuh-indexer.yml` with `uid: wazuh-indexer` (stable, dashboards reference it), URL `${WAZUH_INDEXER_URL}`, root CA loaded with `$__file{}`, flavor `opensearch` 2.19.6 (the indexer's `/` reports 7.10.2 for compatibility), daily index pattern `[wazuh-alerts-4.x-]YYYY.MM.DD` (PROJECT.md D35). `grafana-ro` gained read-only permissions the plugin needs: cluster `cluster:monitor/main` and `cluster:monitor/health` (version and health) and index `indices:admin/get`. Still denied everything outside `wazuh-alerts-*` and all writes. |
| A37 | 1.3 | Grafana admin login | `GRAFANA_ADMIN_USER` / `GRAFANA_ADMIN_PASSWORD` (generated) are applied when Grafana's database is created only; changing them later needs `grafana cli admin reset-admin-password` inside the container, or a new `grafana-data` volume. Sign-up, usage reporting, update checks and the news feed are off. |
| A38 | 1.3 | Starter dashboard | "SOC Overview" (`uid: asox-soc-overview`, folder "ASOX"): a single-series "Alerts over time" line (1-minute minimum bucket, no legend since the title names the series) and a "Recent alerts" table (100 newest: time, level, rule, description, agent, alert ID), both filtered by a "Minimum level" variable (0/3/7/10/12). Checked rendered in light and dark themes. Provisioned with `allowUiUpdates: true`; Grafana re-applies the file within 30 s when it changes. |
| A39 | 1.3 | `grafana-export.sh` | Exports every dashboard (or the given UIDs) through the Grafana API into `provisioning/dashboards/`, overwriting the file that already holds the same UID, else `<title>.json`; drops the per-database numeric `id`. Round trip tested: an edit made through the API shows up in `git diff` as exactly that change, and reverting the file brings Grafana back to it. |
| A40 | 1.3 | `contracts-check.sh` built step by step | Created in step 1.3 with C8; each later step adds its contracts, the others report `SKIP ... (build step N)`, and step 1.7 completes it. Contracts that need a Wazuh alert (C1, C8) share one test alert: fired with `nodes/lab/trigger.sh`, waited for in the indexer (`ALERT_TIMEOUT`, default 120 s), identified by its Wazuh alert ID. C8 = datasource health OK and a query through Grafana (`/api/ds/query`) returning that alert ID. |
| A41 | 1.4 | Webhook token (D36) | `N8N_WEBHOOK_TOKEN` is a `__secret__` in the core `.env`. n8n stores it as the Header Auth credential "ASOX webhook token" (header `X-ASOX-Token`), used by every baseline webhook (`recv-wazuh-alert`, `recv-thehive-event`, `chk-wazuh-api`). Wazuh gets it through the manager's environment: `entrypoint-scripts/20-n8n-integration.sh` writes the `custom-n8n` `<integration>` block (hook URL, token as `api_key`, level) into `ossec.conf` at every start. Missing or wrong token → HTTP 403, verified by C1. Note that `n8n-api` can read the manager configuration (built-in `manager:read`), which includes this token; n8n holds it anyway. For C4 (step 1.7): configure TheHive's webhook to send the same header; if TheHive can only send an `Authorization` header, add a second Header Auth credential for `recv-thehive-event` instead. |
| A42 | 1.4 | n8n environment without secrets (D37) | `N8N_BLOCK_ENV_ACCESS_IN_NODE=false` exposes the container environment to every workflow, so it contains only configuration and service URLs (`WAZUH_API_URL`, `THEHIVE_URL`, `CORTEX_URL`, `N8N_WEBHOOK_URL`). The encryption key (`N8N_ENCRYPTION_KEY`) and the optional Postgres password reach n8n as Compose secrets sourced from `.env` (`/run/secrets/...`, read through `*_FILE` variables). `N8N_WEBHOOK_URL` is also n8n's own setting for its webhook base URL; the deprecated `WEBHOOK_URL` is not used. |
| A43 | 1.4 | n8n memory (D38) | Measured on n8n 2.40.7: ~730 MB peak at every start (all node types loaded; the internal JavaScript task runner adds ~120 MB), ~350 MB steady. At the planned 400 MB limit Node.js derived a ~250 MB heap and crashed with "heap out of memory". Now `NODE_OPTIONS=--max-old-space-size=${N8N_HEAP}` with `N8N_HEAP` 384 / 256 and `N8N_MEM` 640m / 448m (standard / low); both start and stay under their limits. Internal task-runner mode is deprecated upstream (external mode needs another container); kept for now. The Python task runner is not available in the image (warning at start, harmless: JavaScript only). |
| A44 | 1.4 | How workflows and credentials get into n8n | Credentials: `n8n import:credentials` fed through stdin (plaintext is encrypted by n8n; never written to the host), with fixed IDs `asoxWebhookToken`, `asoxWazuhApiRo01`, so exported workflows reference them on every machine. Workflows: `n8n import:workflow` in a one-off container sharing the data volume (the CLI next to the server pushed the 640 MB container to ~600 MB), then activation through the API so the running server registers the webhooks (`--activeState=fromJson` only works in queue mode). Existing active workflows are deactivated through the API before re-import, and activation waits until each authenticated webhook answers (it takes ~0.1 s; a check right after activation otherwise got 404). `bootstrap.sh` imports only workflows n8n doesn't have; `n8n-import.sh` overwrites on request. |
| A45 | 1.4 | n8n API access for scripts | The UI login (`/rest/login`) is rate-limited to 5 attempts per window, which repeated script runs hit. Scripts therefore use the public API (`/api/v1`) with `N8N_API_KEY` (`__bootstrap__`), created by `bootstrap.sh` with only `workflow:list/read/activate/deactivate` and `execution:list/read`, label `asox-scripts`, replaced if it stops working. The UI login is used by `bootstrap.sh` only (owner check, key creation). New helper `env_set` in `scripts/lib/common.sh` writes such values into `.env`. |
| A46 | 1.4 | n8n owner and UI settings | Owner `N8N_OWNER_EMAIL` (`admin@asox.local`) / `N8N_OWNER_PASSWORD` (generated), created by `bootstrap.sh` through `/rest/owner/setup` on first start. `N8N_SECURE_COOKIE=false` (plain HTTP in the lab, PROJECT.md 4.1), diagnostics, version notifications and personalization off, timezone UTC. |
| A47 | 1.4 | Contract checks C1 and C2 | C1: POSTs to `/webhook/wazuh-alert` without a token and with a wrong token must get 401/403; then the shared test alert must appear in a `recv-wazuh-alert` execution (searched through the API with execution data). C2: the `chk-wazuh-api` workflow (called with the token) logs in with the "Wazuh API (n8n-api)" credential, lists agents, and tries `PUT /active-response` with the unknown command `!asox-contract-probe` (harmless even if it were allowed); C2 passes only if that returns 403. New naming prefix `chk-` for contract-check workflows (nodes/core/n8n/README.md). |
| A48 | 1.4 | `custom-n8n` integration | `integrations/custom-n8n` is a copy of the wrapper Wazuh ships for its integrations; `custom-n8n.py` POSTs the raw alert JSON with the token header, 10 s timeout, and logs failures to `/var/ossec/logs/integrations.log`. No retries (n8n backlog: error handling and retries). The files reach `/var/ossec/integrations` through `/wazuh-config-mount` and get `root:wazuh 750` at start. |
