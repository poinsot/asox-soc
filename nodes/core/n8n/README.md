# n8n — SOAR, "Orchestrador"

Owner: Inigo (@poinsot), also the integrator. Branch: `n8n`. Node: `core`. Run mode: `core-cases` (`core` is enough for C1/C2 work).

n8n is the platform's SOAR and integration hub, and the **only** component that executes automated actions that change systems (PROJECT.md 6.2, D12).

**Start here:** [CONTRIBUTING.md](../../../CONTRIBUTING.md) (light rules, exporting changes, onboarding), then this file. First time: `./scripts/soc.sh init core-cases`; then `soc.sh up core-cases` / `soc.sh down`. Test loop: edit a playbook → `nodes/lab/trigger.sh` → check the execution and the TheHive alert → `scripts/n8n-export.sh` (`core-cases` is best effort on 8 GB machines: use a 16 GB+ machine or the shared instance). Details: [PROJECT.md](../../../PROJECT.md) 6.2.

`core-cases` includes TheHive, which turns read-only after a 14-day trial: request and activate your Community license, then back it up right away ([TheHive README](../../cases/thehive/README.md#license-important)).

## Playbook conventions (every workflow author follows them)

- **Naming:** `pb-<use-case>` for playbooks (e.g. `pb-ssh-bruteforce`), `recv-<source>` for entry points, `lib-<function>` for reusable sub-workflows (e.g. `lib-enrich-observable`), `sched-<what>` for scheduled triggers, `chk-<what>` for contract checks.
- **Header note:** a sticky note in every playbook declares **trigger**, **inputs**, **actions taken**, **systems changed** (none / which), **approval** and **owner** (see the stubs). **Approval** always says `required` or `not needed`, with the reason (e.g. `not needed: no system changes`; `not needed: SOC bookkeeping only …`; `required: blocks an IP on an agent`). Every workflow so far is `not needed`.
- **Traceability:** every execution carries the Wazuh alert ID and, once created, the TheHive alert or case ID, and writes a summary of its actions back to the TheHive record.
- **Approval by default:** a playbook that changes systems requires analyst approval unless it is explicitly marked `auto_approve`; justify that marking in the checkpoint pull request. `auto_approve` applies only to playbooks that change systems (response actions, C9, Phase 2); a workflow that changes nothing is `not needed`, never `auto_approve`.
- **Idempotent and safe to re-run:** the same alert processed twice must not create duplicate TheHive records or repeat actions.

### Playbook catalog

**`pb-generic`** (N8N-4.1). *Trigger:* `lib-alert-queue-drain` (the alert queue, N8N-1.4), for every alert `recv-wazuh-alert` hands off (at or above the threshold, not excluded): every routing row names it today, and it is the routing fallback for a row whose playbook isn't built yet. *Input:* the alert, `lib-config` and the route; `caseTemplate` comes from the route, the custom field `playbook` is `pb-generic` (the playbook that ran), and the writeback lists the route (`Route: <route_id> (<matched by>) …`, plus any playbook fallback and proposed matches) after its fixed first line. *Steps:* `lib-normalize-wazuh-alert` → `lib-extract-observables` → `lib-misp-warninglist` (C10, N8N-2.11: warninglist tags on the observables; On Error = continue, MISP unreachable = continue) → `lib-thehive-upsert-alert` → only when the outcome is `created` (a duplicate is not re-enriched): `lib-enrich-observable` (N8N-2.4, Execute Workflow with **On Error = continue**: an unexpected failure is recorded as `enrichment: failed`, never parks and never blocks the writeback) → `lib-thehive-writeback`. **On `duplicate` (repair, N8N-1.4):** `lib-thehive-alert-state` checks for the writeback; without it (an earlier run stopped before writing it: crash, restart), the observables without an `analyzer:` tag are enriched now (same policy) and the writeback adds `Completed an interrupted run …` and `Already enriched before the interruption (not sent again): …`; with it, nothing is repeated. `lib-thehive-writeback` re-checks the marker right before posting, so there is still one writeback. The writeback's first line and marker are unchanged; after the route it lists the enrichment: counts (enriched / skipped / failed, analyzer runs planned, answered from Cortex's cache), then one line per observable: `Enriched: <type> <value>: verdict <v> (<analyzer>: <verdict>, <taxonomies>, job <id>); tagged …`, `Not enriched: … <reasons>`, `Enrichment failed: … <analyzer>: <class> after N call(s)`; a duplicate says `Enrichment: not run (duplicate …)`. **Metrics (C11, N8N-2.9):** before its comment, `lib-thehive-writeback` writes the alert's `asox-metrics` document (created alert: every creation field; duplicate: `n8n_execution_id` only) and the writeback ends with `metrics: ok | skipped (<why>) | failed (<class>)`, also in the result's `metrics`; a metrics failure never parks or blocks anything (see "Metrics (C11)"). *Systems changed:* TheHive (alert, comment, observable tags and IOC flag) and the Wazuh indexer (the alert's `asox-metrics` document); Cortex runs read-only lookups. *Approval:* not needed. *Result:* `outcome` = `created`, `repaired` (the alert existed without a writeback: completed now), `duplicate` (the same Wazuh alert again: nothing new is created or written) `parked` (see `lib-error`; a TheHive outage is retried first, N8N-6.2), or `skipped` (`skipped: TheHive not configured` when `THEHIVE_ENABLED=false`: no park, no writeback); the result also carries `enrichment` (counts, `not run (duplicate)` or `failed`). *Test:* `fixtures/replay.sh --fresh-id --times 2 --delay 5 --file fixtures/wazuh/100100-asox-test-c1.json` → route `wazuh-generic` on the `lib-alert-queue-drain` execution, one `asox-test` alert (severity 3, `caseTemplate` `wazuh-generic`, custom fields filled once TheHive's `entities/` are loaded, observables `ip` of the agent tagged `agent`, `range:internal`, and `hostname` tagged `agent`) with one writeback comment; `19007` (an old level-7 fixture from before Wazuh's SCA tuning, W2.7) → a `wazuh-generic` alert since the SCA exclusion was removed (delete it), `503` → filtered, `invalid/100100-no-id.json` → parked; delete the `asox-test` alerts afterwards. Outage: stop only the `thehive` container (`docker stop`), replay → parked `thehive_unreachable` with `attempts: 3`; start it, wait for healthy, re-run `contracts-check.sh --only C4`. *Enrichment tests* (`full` mode: MISP is needed): `fixtures/replay.sh --fresh-id --file fixtures/synthetic/100100-misp-hit.json` → the seed IOC `101.99.75.184` (X-36; `203.0.113.66` until 2026-10-14) enriched by `MISP_2_1`, verdict `suspicious` (MISP's taxonomy for a hit; MISP finds the seed event and Botvrij's), tags `asox:verdict=suspicious`, `analyzer:MISP_2_1`, `ioc` stays false, the agent's IP and hostname skipped, all listed in the writeback; `--times 2 --delay 30` on it → the second is `duplicate`, no new Cortex job; plain `100100-asox-test-c1.json` → `nothing eligible`, no Cortex call. Outage: `docker stop` only the `cortex` container, replay the MISP fixture with `--fresh-id` → alert created, `Enrichment failed: … MISP_2_1: cortex_unreachable after 3 call(s)`, writeback written, nothing parked (~9 s); `docker start` it and wait for healthy. Measured 2026-10-06: a new MISP job took ~11 s end to end; a second alert on the same IOC within 10 min reused the cached job. Not configured: recreate n8n with `THEHIVE_ENABLED=false` in the shell (`compose core up -d n8n`), replay → `skipped`, then recreate it without the override. **Known limitation:** two copies of one alert processed at the same moment would create two TheHive alerts, because TheHive's duplicate refusal isn't atomic (`docs/ALERT-TO-THEHIVE.md` §2). Through the alert queue they aren't processed at the same moment: a row waits while another row for the same Wazuh alert runs (N8N-1.4). Only a playbook called outside the queue (queue unavailable) can still race.

### Routing (N8N-1.3)

`recv-wazuh-alert` (queues the raw alert) → `lib-alert-queue-drain` → `lib-route-alert` → the chosen playbook. Since N8N-1.8 the route is recorded on the **`lib-alert-queue-drain` execution** (node `Playbook input`, and the `Drain result` line), no longer on the recv execution. The table is **data** in `lib-config` (`routing`), seeded from ALERT-FORMAT §3 (TheHive) on 2026-10-06; order and matches fixed on 2026-10-09 with the Wazuh owner's answers from live alerts (A1–A6 in `nodes/core/wazuh/docs/integrator-requests-2026-10-06.md`) and his rules 100200/100211/100212 (W2.2). **Since 2026-10-14 (version `2026-10-14`, X-04) it is ALERT-FORMAT §3 row for row**: TheHive's `login-bruteforce` row for rule 103011, `ssh-bruteforce` requiring `sshd`, and `network-scan` active. Routing key per D-N2: **rule groups first, then a short rule-ID map** where a group is too broad (e.g. `suspicious-login`), plus MITRE techniques and level. Wazuh rules carry Wazuh's standard groups, never a playbook group (no `pb_*`): which playbook handles what stays n8n data.

- **Rows are ordered; the first `active` match wins.** A `proposed` row that matches is recorded in `proposed_match` (and in the writeback) and evaluation goes on, so its alerts get the default until the row is confirmed (with the Wazuh owner, W1.3, X-04) and switched to `active`. The last row is the default (`wazuh-generic`), and it must stay last.
- **A row:** `{ id, status: 'active' | 'proposed', match: [clause, ...], playbook, case_template, note }`. The row matches when **any** clause matches. A clause matches when **every** key it has matches: `groups_all` (all of these `rule.groups`), `groups_any` (one of them), `rule_ids` (`rule.id`, as strings), `mitre_prefix` (`T1110` matches `T1110` and `T1110.001`, not `T11100`; techniques from `rule.mitre.id`, else `rule.mitre_techniques`), `min_level` (`rule.level` ≥). A clause with no keys never matches.
- **Playbooks:** `playbooks` maps a playbook name to its workflow ID (Execute Workflow by ID). A row naming a playbook that isn't there (not built yet) runs `routing.fallback_playbook` (`pb-generic`) and records `fallback: {wanted, reason}`; it never fails.
- **Defensive:** routing reads the raw alert; a missing or mistyped `rule.groups`, `rule.id` or MITRE field only means "no match", and a malformed alert still reaches the playbook's normalizer, which parks it with its id. Test alerts (rule `100100`, `asox-test`) match no row and take the default.

**How to add or change a row**
1. Edit `routing.rows` in `lib-config`'s `Config` node (UI or file): put the row **before** the default row, in priority order; use `status: 'proposed'` until the rule IDs and groups are agreed with Wazuh (and the template exists in TheHive's `entities/`). Bump `routing.version`.
2. A new playbook: build `pb-<use-case>` with a fixed ID, `"active": true` and the header note, add it to `playbooks`, then point the row's `playbook` at it.
3. Test: replay a fixture (`fixtures/wazuh/` has a real alert for each active row except malware and IDS; or a variant of one with the groups/technique you route on), or run the Wazuh owner's lab scenario (`nodes/lab/trigger.sh --scenario <name>`, list in `fixtures/README.md`), and check the `lib-alert-queue-drain` execution's `Playbook input` (`route`), the TheHive alert's `caseTemplate`, and the writeback's `Route:` line. TheHive silently drops an unknown template (the playbook's writeback warns).
4. `scripts/n8n-export.sh`, review the diff, commit.

### Enrichment policy (N8N-2.4)

What `lib-enrich-observable` does with each observable is **data** in `lib-config` `enrichment`, so the Cortex + MISP owner's `n8n-enrichment.md` (X-06, X-07) and the written TLP/PAP policy (X-08) only change that table:

- **Never enriched:** the agent's own observables (tag `agent`) and internal ranges (`range:internal`): `skip.never_tags`. **Local analyzers only:** documentation ranges (`range:documentation`, e.g. the lab scenarios' attacker addresses): `skip.local_only_tags`. The seed IOC `101.99.75.184` is a public address, so online analyzers will take it once they are enabled. Observables are taken in extraction order, at most `max_observables_per_alert` (10).
- **Analyzers** (`analyzers`, by their Cortex name): `kind` (`local`: no data leaves the lab / `online`), `enabled`, `data_types`, `max_tlp` / `max_pap` (n8n refuses to send an alert above them; Cortex checks again), `timeout_s` (the `waitreport` wait), `quota_note`. Seeded: `MISP_2_1` (local, enabled) and the five online analyzers of `nodes/cases/cortex/analyzers/analyzers.json`, **disabled** until they have keys and `n8n-enrichment.md` confirms their data types and quotas. Jobs run one after another (`concurrency: 1`, the only value supported); `force: false` lets Cortex answer from its job cache.
- **Verdict:** each taxonomy level (`info`, `safe`, `suspicious`, `malicious`) through `verdict.levels`, then `verdict.overrides[<analyzer>]`; the worst wins per analyzer and per observable; no taxonomy = `info`. `ioc: true` only for `ioc_verdicts` (`malicious`, ALERT-FORMAT §5), never set back to false. Each enriched observable gets `asox:verdict=<verdict>` and `analyzer:<name>` tags.
- **Open:** `MISP_2_1` reports a hit as `suspicious`, so a MISP hit is **not** an IOC today, although ALERT-FORMAT §5 gives "an IP found in MISP" as an IOC example. Question sent to Cortex + MISP and TheHive; switching is one override line (`overrides: { MISP_2_1: { suspicious: 'malicious' } }`).
- **Failure semantics:** enrichment never parks the alert, never blocks the writeback and never lowers severity, closes or suppresses anything (D12). Per observable: `enriched`, `skipped` (reasons), `failed` (class, attempts). Cortex down → the analyzer list fails after 3 calls and every job is `cortex_unreachable` (one retried call per alert, not per job).
- **Plugging in `n8n-enrichment.md`:** for each analyzer it lists, set `enabled`, `data_types`, `kind`, `timeout_s`, `quota_note`; put per-analyzer level changes in `verdict.overrides`; bump `config_version`; replay the fixtures above.
- **Values on a MISP warninglist (C10):** an observable carrying the `warninglist` tag (set by `lib-misp-warninglist`, next section) goes to **local analyzers only** while `misp_warninglist.skip_online_analyzers` is true: the online analyzers are skipped with the reason "online, and the value is on a MISP warninglist", which saves their quotas. `MISP_2_1` (local) still runs, so a warninglisted value is both tagged and enriched (e.g. the lab's documentation addresses, on "List of RFC 5735 CIDR blocks"). The seed IOC `101.99.75.184` is on no warninglist (Cortex + MISP's `misp-config.sh apply` fails if it ever is). All online analyzers are disabled today, so the reason shown is "disabled"; the skip was tested with one enabled in a harness only. The policy is the Cortex + MISP owner's: `false` makes a match change nothing in enrichment.

### Warninglist check (C10, N8N-2.11)

Before the TheHive alert is created, `pb-generic` asks MISP once whether the alert's values are on a warninglist (public DNS resolvers, Tor exit nodes, top-site lists, RFC ranges, ...) and marks the ones that are. **A match means common, not safe:** it only adds a tag and a description; `ioc`, severity and status never change and nothing is closed or suppressed (D12, C10).

- **What is checked:** observables whose dataType is in `data_types` (`ip`, `fqdn`, `domain`, `url`, `hash`), minus those carrying a `skip_tags` tag (`agent`, `range:internal`: internal addresses would all match the RFC 1918 list). Documentation ranges are checked. One `POST {{ $env.MISP_URL }}/warninglists/checkValue` with all values, credential "MISP API (n8n)" (Read Only user), "Ignore SSL Issues" on. No call when nothing is eligible (the plain test alert) or when `enabled` is false.
- **Tag and description** (answer G as revised by the TheHive and Cortex + MISP owners, 2026-10-14; applied 2026-10-15): the tag `warninglist` once, and **every** matching list's full name in the observable's `message` (TheHive's observable description, shown when the analyst opens it; no cap):
  ```
  On MISP warninglists (common, not safe):
  - List of known IPv4 public DNS resolvers
  - Specialized list of vpn-ipv4 addresses belonging to common VPN providers and datacenters
  ```
  Names containing one of `prefer` (`public DNS`, `Tor exit`; case-insensitive, in that order) go first, then the others by name; MISP's own order isn't used (it follows list IDs, which depend on the instance). An observable that already has a `message` gets the note after a blank line. No `warninglist:<list name>` tags any more (they were cut off at ~25 characters in TheHive's list and pushed `src` / `dst` / `asox:verdict=` behind "Show more"). Tag and message travel in the alert-creation body, so there is no extra TheHive call; on a duplicate the check runs but writes nothing. TheHive keeps the `message` when the alert is promoted: the case's observables carry the same text (checked 2026-10-15, `docs/ALERT-TO-THEHIVE.md` §9).
- **Settings** (`lib-config` `misp_warninglist`): `enabled`, `tag` (`warninglist`), `lists_in_message` (true), `list_tag_prefix` and `max_list_tags` (0: no per-list tags), `prefer`, `data_types`, `skip_tags`, `timeout_ms` (5000), `skip_online_analyzers` (see "Enrichment policy"; it keys on `tag`, which stays). The old behaviour (tags `warninglist:<list name>` for 3 lists, no message) is `max_list_tags: 3`, `lists_in_message: false`.
- **Writeback:** `Warninglists (MISP, C10): 3 of 3 checked value(s) on a warninglist; a match means common, not safe: severity and status unchanged.`, then one `On warninglist: <dataType> <value>: <list names, at most 10, then "+N more">; tagged warninglist.` line per match (the full list is in the observable's `message`). On a duplicate the summary ends `Checked, tags not written (alert already existed).` (in the execution's `Writeback input`; the TheHive comment is written once).
- **Failure behaviour:** one call, no retry. MISP unreachable (`misp_unreachable`), a timeout (`timeout`), another HTTP status (`http_<code>`), HTTP 200 without JSON (`bad_answer`) or an unexpected error in the lib: the observables go on **untagged** (no message either), the writeback says `Warninglist check (MISP, C10): not done (<class>); alert unaffected.`, and nothing is parked. An empty answer (`[]`) is a normal "no match".
- **How to test** (needs `full`): `nodes/core/n8n/fixtures/replay.sh --fresh-id --file nodes/core/n8n/fixtures/synthetic/100100-warninglist-demo.json`, then look at the `asox-test` alert's observables and writeback in TheHive (expected result in `fixtures/README.md`). Outage: `docker stop` the `misp-nginx` container, replay, start it again. Contract: `scripts/contracts-check.sh --only C10`.
- **Measured (2026-10-10, 800m):** 20 parallel deliveries of the demo alert: every 200 within 1.3 s, all 20 written back once in 83 s; n8n anon peak 590 MiB, misp-core 453 MiB (of 900m; the queue's 2 slots mean at most 2 calls at a time), no OOM kill.

### Metrics (C11, N8N-2.9)

n8n keeps one `asox-metrics` document per Wazuh alert in the Wazuh indexer (document ID = Wazuh alert ID, D-N1) for Grafana's MTTD / MTTA / MTTR and false-positive panels (PROJECT.md 5, C11; `docs/reply-grafana-c11.md`). The only writer is `lib-metrics-upsert`, as `n8n-indexer` (credential "Wazuh indexer (n8n-indexer)", certificate verified).

| Field | Written by | When, and from where |
|---|---|---|
| `alert_id`, `thehive_alert_id`, `rule_id`, `rule_level`, `severity`, `playbook`, `n8n_execution_id`, `outcome` (`none`), `auto_promoted` (`false`), `t_event`, `t_alert` | `lib-thehive-writeback` (mode `create`) | `pb-generic` created the TheHive alert. `t_event` = the Wazuh alert's `timestamp`; `t_alert` = the TheHive alert's `_createdAt` |
| `t_attack_start` | same | lab scenario alerts only: the `asox_run=<id>` in `full_log` → the first attack-start marker (rule 100101) with that `data.run_id` in `wazuh-alerts-*`, **only when it lies between `t_event` − 1 h and `t_event`** (`metrics.attack_start.window_s`, 3600; since 2026-10-15). Otherwise it stays empty and the reason is in the result (`notes`, `attack_start.reason`) and in the writeback as a `metrics note:` line: a replayed fixture keeps its old run id, whose marker would give a MTTD of days (found with A99's E2E check) |
| `n8n_execution_id` | `lib-thehive-writeback` (mode `update`) | a duplicate delivery (the alert existed): nothing else, never `t_alert`. A **repaired** run (the alert existed without its writeback, so without its document) writes every creation field like a new alert |
| `t_ack` | `recv-thehive-event` (mode `update`) | alert status leaves New (also on promote, merge, case created from it, ignore) |
| `resolution`, `t_closed` | same | alert ignored (`Ignored`) or closed with another status; case closed (`stage: Closed`): the case `status` (`TruePositive`, `FalsePositive`, `Duplicated`, `Indeterminate`, `Other`) on each of the case's alerts, read from TheHive |
| `case_id`, `t_case` | same | alert promoted or merged (`caseId`), case created from an alert (`fromAlert`) |
| `severity` | same | an alert or case update carrying `severity` (case: on each of its alerts) |
| `t_contained` | nobody yet | only once C9 exists (Phase 2); MTTR falls back to `t_closed` |

- **Times** come from the source records, never from n8n's clock: the Wazuh `timestamp`, TheHive's `_createdAt`, and for C4 events the **audit record's top-level `_createdAt`** (the event's own time; the object's `inProgressDate` / `endDate` differ by under a second in the fixtures). All are written as ISO 8601 UTC.
- **First-time fields** (`t_event`, `t_alert`, `t_ack`, `t_case`, `t_contained`, `t_closed`, `t_attack_start`) are written only when the document doesn't have them: a painless script in the update (`lib-config` `metrics.first_time_fields`). So `t_ack` stays the first acknowledgement, and a replay never moves `t_alert`. Every other field is overwritten with the latest value.
- **Only the template's 18 fields** go out (`lib-config` `metrics.fields`, the same names and types as the index template; the mapping is strict), with nulls dropped and values typed (`alert_id` a string, `rule_level` / `severity` integers). Anything else is dropped before the write and listed in the result's `dropped`.
- **No document** for test alerts (`source` `asox-test` and the C3 check's `contract-check`, `metrics.skip_sources`); `chk-metrics` writes and deletes its own `outcome: contract-check` document. A C4 event never creates a document (mode `update`): an alert from before N8N-2.9, or one n8n didn't create, is `skipped (no document)`.
- **Never blocks:** no park, no error workflow, On Error = continue at both call sites. Connection errors, timeouts and 5xx are retried twice (`metrics.retry_waits_s`, 2 s then 5 s; timeout 5 s per call), then `failed (unreachable)` / `failed (server_error)`; 400 / 401 / 403 / a missing index are `failed (config)`, not retried; 409 after `retry_on_conflict=3` is `failed (conflict)`.

**How to read the result.** The TheHive writeback comment ends with one line: `metrics: ok`, `metrics: skipped (<why>)` or `metrics: failed (<class>)`; the same line is in `pb-generic`'s result (`metrics`). For C4 events, `recv-thehive-event`'s last node `Event result` lists `<Wazuh alert id>: metrics: …` per document and keeps the full results (`metrics_results`). Failed `lib-metrics-upsert` executions are saved; successful ones aren't (N8N-6.5).

| Line | Meaning | What to do |
|---|---|---|
| `failed (unreachable)` / `failed (server_error)` | the indexer was down or erroring for 3 calls (~7 s plus timeouts) | check `wazuh-indexer`; the document misses this write (no replay queue). A later C4 event can't recreate a missing document; replaying the alert (`replay.sh` with its id) does |
| `failed (config)` | 400 (field or value refused by the strict mapping), 401 / 403 (credential or role), 404 on the index | the result's `message` says which; a missing index or a template change is the integrator's (`bootstrap.sh core`), never n8n's |
| `failed (conflict)` | concurrent writes still conflicting after 3 retries | rare; replay or let the next event write |
| `failed (unexpected)` | `lib-metrics-upsert` itself failed | open its failed execution |
| `skipped (no document)` | C4 event for an alert without a document | expected for alerts from before N8N-2.9 or not created by n8n |
| `skipped (test source asox-test)` | test alert | expected (C11 clarification) |

**Known limits (2026-10-14):** an analyst change within the seconds between the TheHive alert's creation and its writeback finds no document yet (`skipped (no document)`), so that `t_ack` is lost; a marker indexed after the writeback leaves `t_attack_start` empty (the result's `notes` say `no marker … (yet)`), and so does a marker outside the one-hour window (`… outside the 3600 s window`, or `… after t_event`); events caused by `n8n@asox.local` are dropped by loop prevention, so a future n8n auto-promotion (D-N4) must write `t_case` itself; deletes are not tracked (a deleted case leaves `case_id`), and a reopened case keeps its first `t_closed` while `resolution` follows the latest close.

**Test:** `fixtures/replay.sh -f <copy of fixtures/wazuh/5763-sshd-bruteforce.json with a new id>` (not an `asox-test` fixture: those get no document), then read the document as `n8n-indexer`; change the TheHive alert's status, promote, close, ignore, and read it again (N8N-2.9 in the backlog lists the full set, measured 2026-10-14).

### Sub-workflows and error handling

- **Reference sub-workflows by ID** (Execute Workflow node, source "Database", "By ID"). Workflow IDs survive import on every machine: `bootstrap.sh` and `n8n-import.sh` import the files with their own `id`. The SOAR's IDs are fixed and readable (`asoxLibConfig001`, `asoxPbGeneric001`, `asoxLibRouteAlrt`, …), 16 characters like n8n's own; the one exception, `asoxLibThTagObs` (15), stays: renaming it would change its callers' references and the workflow on the live instances (listed in the lint). A playbook can also be called by an ID chosen at run time (`lib-alert-queue-drain`'s `Playbook (by route)`: `={{ $json.route.playbook_id }}`).
- **Sub-workflows must be active (published):** n8n 2.40.7 runs the published version of a called workflow and fails with "Workflow is not active" otherwise; an inactive error workflow is skipped with only a log line. Every `lib-`/`pb-` file keeps `"active": true`.
- **Error workflow:** `recv-n8n-error` on entry workflows (`recv-`, `pb-`; today `recv-wazuh-alert`, `recv-thehive-event`, `recv-n8n-start`, `pb-generic`), not on `lib-` workflows: n8n fires the error workflow for a failing sub-workflow **and** for its waiting caller, so setting it on both reports each error twice. Handle expected failures (TheHive HTTP errors, malformed input) explicitly with `lib-error`, which keeps the Wazuh alert id; n8n's Error Trigger has no input data.
- **TheHive calls: timeout and retries (N8N-6.2).** Every TheHive HTTP call has `lib-config`'s `thehive_http.timeout_ms` (10 s). A connection error, a timeout or HTTP 5xx is retried after `thehive_http.retry_waits_s` (2 s, then 5 s: 3 calls in total); a 4xx is never retried. Pattern (copy it for new calls): HTTP node with `neverError` and the error output → `Assess: <call>` (Code; the call count is its `$runIndex`) → `Retry: <call>?` → `Wait before retry: <call>` → the call again; otherwise `Answered: <call>?` → the interpreting node or `Error input`. After the last call the alert is parked by `lib-error` with `attempts` and `retry_exhausted`. A create that timed out may have succeeded: the retry then gets "already exists" and returns the existing alert (`after_retry: true`). Measured 2026-09-30 with the `thehive` container stopped: 3 calls, parked `thehive_unreachable` after ~9 s, alert id and payload kept.
- **Cortex calls (N8N-6.2, C6):** the same pattern with `lib-config` `cortex_http` (10 s, retries after 2 s and 5 s), one call per execution (`lib-cortex-job`, so `$runIndex` counts that call's attempts). `waitreport` is Cortex 4.1's blocking wait for a job (`atMost`, as C7 uses it): one call instead of a polling loop; its HTTP timeout is `timeout_s` + 5 s, and a client timeout there is not retried (it already waited the job's budget) but ends as `timeout`. Retrying the run call is safe with `force: false`: an accepted run comes back from the job cache as the same job. Loops over jobs and observables use **Loop Over Items** + Execute Workflow (n8n 2.40.7 marks the "run once for each item" mode deprecated).
- **TheHive not configured (`THEHIVE_ENABLED=false`).** On a machine running `core` without the cases node, every alert would otherwise be parked as `thehive_unreachable`: a stopped TheHive and one that was never deployed give the same `ENOTFOUND`, and the TheHive credential exists with an empty key either way. So n8n reads `THEHIVE_ENABLED` (non-secret): `false` → `pb-generic` records `skipped: TheHive not configured`, nothing is parked; unset or anything else → TheHive is expected, and an outage is retried, then parked. `render-env.sh` renders it into `nodes/core/.env` (R-18, A79: `true` when `THEHIVE_N8N_API_KEY` is non-empty); `compose.yml` defaults it to `true` when unset.

## Webhooks are authenticated

Every webhook uses **Header Auth** with the shared token `N8N_WEBHOOK_TOKEN` (from `nodes/core/.env`); without it n8n answers 403 (PROJECT.md D36). There are two credentials for it, because TheHive's webhooks can't send custom headers (D43):

- **"ASOX webhook token"**: callers send `X-ASOX-Token: <token>`. Wazuh (C1) and the contract checks use it. Use it on any new webhook that another system calls.
- **"ASOX webhook token (Bearer)"**: callers send `Authorization: Bearer <token>`. Only for webhooks TheHive calls (`recv-thehive-event`).

## Alert queue (N8N-1.4)

**Why:** `pb-generic` ran detached and unbounded, so a burst ran every playbook at once. On 2026-10-09, 7 alerts in 6 s took n8n from ~340 to 730 MiB of anonymous memory and the kernel killed it (cgroup OOM kill at the 750m limit, not a Node heap error: the old space is capped at 384 MB, the rest is young generation, buffers and the task runner). Alerts in flight lost their writeback. Uncapped, 10 alerts need ~900 MiB and 20 ~1 GiB. n8n's own `N8N_CONCURRENCY_PRODUCTION_LIMIT` can't be used: in 2.40.7 a queued webhook execution also delays its HTTP 200 (measured up to 9.5 s against C1's 10 s timeout), so it would lose alerts at the source.

**How:**
- `recv-wazuh-alert` inserts one row into the n8n Data Table `asox_alert_queue` (`alert_id`, `payload` = the raw alert, `status` `pending`; `playbook_id` is `none` until the drain routes the alert) and **then answers 200** (N8N-1.8; C1's path, token and payload are unchanged, and a single 200 takes ~0.1 s). Until 2026-10-10 it answered on receipt and routed before the insert: see "Parallel deliveries".
- `sched-alert-queue` runs every 5 s. Each run that finds work takes one of the `alert_queue.slots` (2) slot rows in `asox_queue_slots`, then **drains rows one after the other** (N8N-1.7): claims the **oldest** pending row (FIFO by row id), runs `lib-alert-queue-drain` for it, and goes on with the next one until no pending row is left, `max_rows_per_run` (10) rows were drained or `max_run_s` (240 s) has passed (checked before each claim: a row in progress always finishes). Then it frees the slot, and the next tick (≤ 5 s) takes it again if rows are waiting. So at most 2 playbooks run at once; with both slots held, a tick does nothing. Before each claim the run refreshes its slot's `held_ms` (compare-and-set on its token, read back; a lost slot ends the run), so a held slot is never older than its current row and the slot lease below stays valid for long runs. A row the run couldn't finish (claim lost to the other slot, given back, failed attempt) is skipped until a later run, so a failing row is never retried at once; a `lib-alert-queue-drain` failure ends the run. The bound exists because one run's executions stay in memory until it ends; the run itself keeps only row ids, outcomes and durations (`Record row`, ~30 KB of run data per row).
- **No double processing:** every claim is a compare-and-set: `UPDATE … WHERE id = X AND status = 'pending' AND claim = <seen>` sets a new random token, then the row is read back and the run goes on only if the token is its own. Slots work the same way. (The Data Table node's own "returned rows" can't be trusted for this: on SQLite it selects first and updates second.) A row also waits while another row for the **same Wazuh alert** runs and was claimed first (no concurrent copies, A78; since N8N-1.9 the earlier claim time `started_ms` decides, then the lower id), and is finished as `duplicate_delivery` without running when a row for that alert is already `done` ("Duplicate deliveries"). Forced tests: 25 concurrent scheduler runs on 5 rows → 10 lost the slot, 4 lost the row, 5 ran: one drain per row (N8N-1.4); with the N8N-1.7 loop, 10 concurrent runs on 8 rows → 6 lost the slot, 2 found none free, the 2 slot holders drained 3 and 7 rows and collided twice on a row (the loser went on to the next): one drain per row, one TheHive alert and one writeback each. **Don't force 25 concurrent runs any more:** on 2026-10-09 that alone took n8n from 302 to 707 MiB in 2 s and the kernel killed it (cgroup OOM at 750m) before any run reached a slot (~16 MiB per concurrent execution). Real ticks never overlap like that (one every 5 s); the queue lost nothing (rows stayed `pending`).
- **Retries:** a failed playbook run puts the row back to `pending`; after `max_attempts` (3: a crash counts) it is `failed` and parked through `lib-error` with the Wazuh alert id (`error_class: queue_attempts_exhausted`). `parked` from the playbook itself is final (the playbook already retried TheHive, N8N-6.2).
- **Running too long:** a row still `running` after `running_timeout_s` (**2700 s**) is requeued by the scheduler. The value is above the slowest `pb-generic` with every call timing out and retried: TheHive ~4 × 37 s, 10 observables × MISP (37 s submit + 60 s `waitreport`), 10 tag writes × 37 s ≈ 27 min. Normal runs take 1–11 s. Recheck it when online analyzers are enabled (N8N-2.4). A slot is taken back after the row timeout + 300 s.
- **Crash or restart:** `recv-n8n-start` runs when n8n starts. It frees the slots and requeues the rows the stopped process left `running` (claimed more than `restart_grace_s` = 5 s before the start: a restart takes longer), and the scheduler picks them up. Their playbook run finds the TheHive alert already there and **repairs** it (outcome `repaired`, see `pb-generic`). Pending rows simply wait. **No replay is needed.** Measured: n8n killed with 1 row running and 9 pending → all 10 done ~60 s after the restart, 1 `repaired` on attempt 2, one TheHive alert and one writeback each.
- **What is still lost:** since 2026-10-20 (X-10 live, D51; PROJECT.md 5, "C1 delivery and retries") Wazuh's `custom-n8n.py` **retries** connection errors, timeouts, HTTP 404 and 5xx (waits 2, 5, 10, 20 s; a 300 s fast-fail of one try per alert after an exhausted chain), so alerts sent **while n8n is down** (~20–25 s per restart) and deliveries cut off by a crash before their row is written (none of them got a 200 since N8N-1.8, "Parallel deliveries") are sent again; a repeated id answers 200 `duplicate`, final ("Duplicate deliveries"). Still lost: an outage longer than the chain (~37 s refused, ~87 s hanging) or inside the fast-fail window (logged in `integrations.log`), and the alerts queued in integratord when the **manager** restarts (they stay in the indexer). The queue makes such restarts rare: no burst measured here, back to back or 60 at the same instant, took n8n above ~600 MiB ("Parallel deliveries").
- **Housekeeping:** `done` rows are deleted after `keep_done_h` (24 h), by the scheduler and at start-up. `failed` rows stay (they are also parked) until deleted by hand.
- **Execution history:** `sched-alert-queue` saves failed runs only, so its ~17,000 idle runs a day keep nothing. `lib-alert-queue-drain` saves one execution per processed row (~36 KB: the row with its alert, `lib-config`, the playbook's short result; its `Drain result` line gives the outcome, the duration, the row's place in the scheduler run and the queue depth when that run started).
- **Settings:** `lib-config` `alert_queue` (`slots`, `max_attempts`, `running_timeout_s`, `slot_margin_s`, `restart_grace_s`, `keep_done_h`, and N8N-1.7's `max_rows_per_run` = 10 and `max_run_s` = 240: rows and time per scheduler run; without them a run drains one row, as before). The table names are fixed in the workflows (Data Table nodes find tables **by name, as a substring match**: don't create another Data Table whose name contains `asox_alert_queue` or `asox_queue_slots`).
- **Data Tables (n8n 2.40.7, checked 2026-10-09):** Community feature (no license flag), stored in n8n's SQLite (so `backup.sh core` includes the queue). Limit: 200 MB for all tables together (`N8N_DATA_TABLES_MAX_SIZE_BYTES`); a queued row is ~5–15 KB. `recv-n8n-start` creates the tables with "reuse existing" (idempotent: on start-up, re-import and a fresh `bootstrap.sh core`, which publishes the workflow). If the table is missing anyway, `recv-wazuh-alert` runs the playbook directly.

**Queue depth:** the last `lib-alert-queue-drain` execution's `Drain result` line (`queue when the run started: N pending, M running`; with N8N-1.7 a run can be older than the line, see `row k of this scheduler run`), the n8n UI (Overview → Data tables → `asox_alert_queue`), or from the shell (read-only):

```bash
docker exec asox-core-n8n-1 node -e "const s=require('/usr/local/lib/node_modules/n8n/node_modules/sqlite3');const d=new s.Database('/home/node/.n8n/database.sqlite',s.OPEN_READONLY);d.get(\"SELECT id FROM data_table WHERE name='asox_alert_queue'\",(e,t)=>d.all('SELECT status,count(*) n FROM data_table_user_'+t.id+' GROUP BY status',(e2,r)=>console.log(r)))"
```

**Throughput (N8N-1.7):** both slots now stay busy while rows wait, with ~0.1 s between two rows of a run; the only waits left are the first tick (≤ 5 s) and the second slot starting one tick later. 20 real alerts are written back in ~32–34 s instead of ~100 s (~35–40 alerts a minute with fast runs, against ~12); slow runs (new MISP jobs, ~10 s each) already used both slots, so 10 slow alerts take ~56 s as before. A burst's time depends on Cortex's cache: a MISP job for an IOC seen in the last 10 minutes takes ~1 s instead of ~10 s. **Memory cost:** with both playbooks running back to back, n8n's peak rises from ~460 to ~550 MiB for a 20-alert burst (V8 frees less while it works without pauses; it is not data kept per row: 3-row runs peak the same, and memory falls back to ~390 MiB after the burst). ### Parallel deliveries (N8N-1.8, X-35)

Every burst above was sent back to back. Whether Wazuh's integratord can deliver several alerts **at the same time** is an open question to the Wazuh owner (X-35), so the worst case was tested on 2026-10-10 with 20 real fixtures POSTed at once (fresh ids):

- **Before N8N-1.8, at 750m: n8n was OOM-killed and all 20 alerts were lost after their 200.** Each delivery ran `lib-config`, `lib-route-alert` and five Code nodes before the queue insert, about 60 executions at once: 334 → 505 MiB in 0.7 s, then a cgroup OOM kill (main process at 653 MB RSS). All 20 `recv-wazuh-alert` executions ended `crashed` before their insert: no row, nothing to requeue at start-up, and Wazuh had a 200 for each.
- **N8N-1.8:** `recv-wazuh-alert` is now webhook → level check (an IF node on `$env.WAZUH_ALERT_MIN_LEVEL`) → Data Table insert of the raw alert → Respond 200. **A 200 means the alert is in the queue** (or filtered); if n8n dies first, the delivery fails (connection closed, no HTTP status) and Wazuh's `integrations.log` shows it. Exclusions and routing moved to `lib-alert-queue-drain`, behind the 2 slots.
- **Bound on the deliveries themselves: `N8N_CONCURRENCY_PRODUCTION_LIMIT=10`** (`compose.yml`). The insert-first change alone still let 40 deliveries at once get n8n OOM-killed at 750m. With the limit, at most 10 webhook and trigger executions run at once and the others wait in n8n; 20 / 40 / 60 at once all pass (below). What it counts in 2.40.7 (`concurrency-control.service.js`): execution modes `webhook`, `trigger` (the `sched-alert-queue` ticks and `recv-n8n-start` included) and `chat`; **not** sub-workflows (`integrated`), error workflows, manual runs or retries. `sched-alert-queue` holds at most 2 of the 10 for up to 240 s (one per queue slot), so 8 are always left for webhooks: 10 deliveries sent at once while a 20-alert drain held both slots were all answered within 1.0 s, and C1, C3, C4 passed right after a burst. This limit was rejected on 2026-10-09 because a waiting delivery delayed its 200 by up to 9.5 s; a recv execution then ran sub-workflows and Code nodes, now it takes ~50 ms, and the answer already waits for the insert.
- **How long a 200 takes:** n8n handles a delivery in ~50 ms on one thread, so N at once take N × ~50 ms: 10 → 0.6 s, 20 → 1.2 s, 40 → 2.1 s, 60 → 3.0 s. The criterion is every 200 under 5 s (half of `custom-n8n.py`'s 10 s timeout), which holds up to about 100 deliveries at the same instant by that slope (not measured beyond 60).

### Duplicate deliveries (N8N-1.9, X-10)

The condition n8n set for Wazuh's C1 retries (`docs/reply-wazuh-x10.md`, condition 3; the retries are live since 2026-10-20: PROJECT.md 5 "C1 delivery and retries", D51, Wazuh PR #31): a retry after a timeout can deliver an alert that n8n had already queued, and TheHive's own duplicate refusal isn't atomic (A78). Two guards keep a repeated delivery to **one queue run, one TheHive alert and one writeback**:

1. **At intake (`recv-wazuh-alert`):** before the insert, node `Known alert id? (asox_alert_queue)` looks up a row with the delivery's alert id and a status other than `failed` (so `pending`, `running` or `done`; done rows are kept `keep_done_h`, 24 h). A hit answers **HTTP 200 `{"status": "duplicate"}`** and writes nothing; node `Duplicate` records `duplicate delivery: row N of asox_alert_queue (<status>) has this Wazuh alert id; not queued again (N8N-1.9)`. A `failed` row doesn't count: a new delivery may retry an alert whose attempts ran out. A lookup error goes on to the insert (and, if the table is really gone, to the queue-unavailable branch), so the guard never loses an alert. The three answers are `queued`, `duplicate` and `filtered` (plus `accepted, not queued` when the table is unavailable). Wazuh's `custom-n8n.py` (branch `wazuh-x10`) treats every 2xx as delivered, so a `duplicate` is never retried.
2. **Before a row runs (`lib-alert-queue-drain`):** node `Same alert running or done` reads the other rows for the alert id that are `running` or `done`. A `done` copy → this row is finished `done` with outcome **`duplicate_delivery`** (note `duplicate delivery: row N for the same Wazuh alert is done (<outcome>); not run again (N8N-1.9)`), no playbook. A `running` copy claimed first (earlier `started_ms`, then lower id) → the row is given back to `pending` (attempt not counted) and a later scheduler run sees the copy `done`.

**Why two: the Data Table gives no atomicity here.** The lookup and the insert are two nodes, i.e. two separate statements on n8n's SQLite, and other executions run between them (Node's event loop interleaves executions at every database call). Data Table columns can't be declared unique, and the node's `upsert` (an update-then-insert in one TypeORM transaction) would overwrite the existing row (a `done` row back to `pending`), so it can't serve as insert-if-absent. So two copies arriving within the same few milliseconds can both pass the lookup and both be inserted. Measured 2026-10-15: of 4 trials sending 2 or 5 copies of one id at the same instant, 3 inserted two rows (the 5-copy trial: 2 `queued`, 3 `duplicate`); in every case the drain finished the second row as `duplicate_delivery`: one TheHive alert, one writeback. The drain guard is also not atomic on its own (read, then act), but the scheduler's compare-and-set claims and the claim-time order mean that of two copies at most one runs at a time, and a copy that finishes first makes the other one end as `duplicate_delivery`.

**Measured 2026-10-15** (build instance, `full`, `standard`, n8n 800m, `5763-sshd-bruteforce.json` copies with fresh ids):

## Operations

- **UI:** `http://localhost:5678`, login from `scripts/soc.sh info`.
- **Executions** are pruned after `N8N_EXECUTIONS_MAX_AGE_HOURS` (168 h) or beyond `N8N_EXECUTIONS_MAX_COUNT` (10,000): the lab agent alone forwards many level 7+ alerts. `recv-*`, `pb-*` and `chk-*` save every execution; `lib-*` save only failed ones (N8N-6.5): the calling playbook's execution holds each lib's result. Exceptions: `lib-alert-queue-drain` saves every run (one per processed alert), `sched-alert-queue` only failed runs (N8N-1.4).
- **Saved executions contain the webhook token (N8N-6.5, known limitation).** A `recv-*` execution stores the webhook request as received, headers included: `x-asox-token` (C1, `recv-wazuh-alert`) and `authorization: Bearer …` (C4, `recv-thehive-event`), in clear. There is no clean way to keep them out (checked on 2.40.7, 2026-09-30): the Webhook node's output is saved as is and later nodes can't rewrite it; recv executions must be saved because the C1 and C4 checks look for their test alert there; n8n's execution redaction is an Enterprise feature (off on Community) and only masks data when it is read, not in the database; and the Webhook node's own "sensitive fields" list names `authorization` but not `x-asox-token`, and wasn't applied here either (both tokens came back in clear through the API).
  - **Anyone who can read executions can read the token**, and with it post alerts to n8n. Today that is the n8n owner account (UI) and the scripts' API key (`N8N_API_KEY`, scope `execution:read`), which lives in `nodes/core/.env` next to the token itself. Treat execution access as secret: don't create other n8n users with access to the SOAR's workflows, and don't share execution screenshots or exports of `recv-*` executions.
  - **Retention:** up to 168 h / 10,000 executions, in the `n8n-data` volume. `scripts/backup.sh core` archives that volume, so **core backups contain the token: treat them as secret** (like `--with-secrets` backups).
  - **If it leaks, rotate it** (in this order; done on 2026-10-20). Bootstrap must run after the containers carry the new value, or the n8n credentials and TheHive's webhook disagree with n8n (C4 answers 403).
    1. Remove `N8N_WEBHOOK_TOKEN` from `nodes/core/.env`, then run `scripts/render-env.sh` (new secret). Single-host mode copies it to `nodes/cases/.env`; distributed mode: paste it into `nodes/cases/.env` on the cases machine.
    2. `scripts/soc.sh up full`: recreates n8n and the Wazuh manager with the new value (C1). Never a raw `docker compose up`: `soc.sh` attaches `soc-net` itself, and a manager without it cuts off the lab agent (C1 then fails with "not indexed").
    3. `scripts/bootstrap.sh core` (n8n credentials), then `scripts/bootstrap.sh cases` (TheHive's webhook, C4).
    4. Restart the lab agent (`docker restart <instance>-lab-lab-agent-1`) and wait until `agent_control -l` shows it Active.
    5. `scripts/contracts-check.sh --only C1,C3,C4,E2E`.
- **Memory:** n8n 2.x peaks at ~500–560 MB of anonymous memory while it starts, then settles at ~300–350 MB. Bursts go through the alert queue (above): at most 2 playbooks at once, ~460–575 MiB peaks; at most 10 webhook and trigger executions run at once (`N8N_CONCURRENCY_PRODUCTION_LIMIT`), and 20–60 deliveries at the same instant peak at 561–598 MiB ("Parallel deliveries"). The Node.js heap is set by `N8N_HEAP` (384 MB standard / 320 MB low) and the container limit by `N8N_MEM` (800m standard / 650m low; R-26, A91; `low` measured on 2026-10-13 needs 800m by D40, proposed to the integrator, "Parallel deliveries"), with swap capped at the limit (PROJECT.md D38, D40). If n8n logs `JavaScript heap out of memory`, the heap is too small, not the container.
- **PostgreSQL** (optional, profile `pg`): export all workflows, uncomment the `DB_*` lines in `compose.yml`, and ask the integrator to enable the profile (`COMPOSE_PROFILES=pg` in the core `.env`, which `soc.sh` doesn't manage yet); then restart core and re-run `bootstrap.sh core` and `n8n-import.sh`. Switching is the n8n owner's decision.
- Scripts use n8n's public API with `N8N_API_KEY` (limited scopes, created by `bootstrap.sh`), because the UI login is rate-limited to 5 attempts per window.
