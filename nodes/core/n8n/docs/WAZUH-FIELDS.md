# Wazuh alert fields n8n relies on (N8N-0.3)

Owner: n8n (Inigo). **Status: DRAFT promise, to agree with the Wazuh owner (Daniel) at checkpoint 1, 2026-10-20** (X-01, Wazuh W2.5). C1's payload shape doesn't change (PROJECT.md 5); this file only turns the fields n8n reads into a documented promise, so a rule or decoder change on the Wazuh side that drops or retypes one of them is agreed first.

**Verified against the fixtures, not from memory** (`../fixtures/wazuh/`, captured 2026-09-30 from the build instance, Wazuh 4.14.8). The lab produces only three rule types at level ≥ 7 today, so many fields below are **not seen yet**. Their row says so, and they must be re-checked when Wazuh's scenarios (X-05, `trigger.sh --scenario`, 2026-10-09) and Suricata (M3, 2026-11-03) produce real alerts.

## Core fields (every alert)

| Field | Type (seen) | Carried by | Not carried by | Promise | Notes |
|---|---|---|---|---|---|
| `id` | string, `"<epoch>.<offset>"` (e.g. `"1790461241.14189"`) | all | — | **required** | Dedup key everywhere: TheHive `sourceRef` (D-N1), C11 document ID. Keep it a string: it looks like a decimal number, and parsing it as one loses digits (`Number("1790378132.1860721")` is `1790378132.186072` in n8n's Node.js). |
| `timestamp` | string, `YYYY-MM-DDTHH:MM:SS.mmm+0000` | all | — | **required** | The offset has **no colon** (`+0000`). Inside n8n both JavaScript `Date.parse` and Luxon `DateTime.fromISO` accept it (checked in the n8n 2.40.7 container), but stricter parsers don't (jq's `fromdateiso8601` rejects it): the normalizer emits a canonical ISO/epoch value so later steps and other tools don't depend on this format. Source of C11's `t_event` and TheHive `date`. |
| `@timestamp` | string, ISO with `Z` | indexer copies only | **C1 body** | never use | Added by the indexer pipeline, like `input.type`; not in the C1 POST. |

## MITRE ATT&CK

| Field | Type (seen) | Carried by | Not carried by | Promise | Notes |
|---|---|---|---|---|---|
| `rule.mitre.id` (and `.tactic`, `.technique`) | **not seen** | — | all four | **optional** | PROJECT.md, ALERT-FORMAT §1/§3/§4 and n8n's backlog assume `rule.mitre.id`. None of today's alerts has a `rule.mitre` object. Expected to be an **array** of technique IDs on rules with a `<mitre>` block (e.g. sshd brute force): to confirm with a real alert (X-05). |
| `rule.mitre_techniques` | array of strings (`["T1003","T1003.008","T1222","T1222.002"]`) | sca-check | test, sca-sum, agent | optional | How **SCA** alerts carry MITRE: a different path from `rule.mitre.id`. Together with `rule.mitre_tactics` (`["TA0005"]`) and `rule.mitre_mitigations`. |
| `data.sca.check.compliance.mitre_techniques` | string, comma-separated (`"T1003,T1003.008,…"`) | sca-check | others | optional | Same list as a comma string; don't use it when `rule.mitre_techniques` is present. |

**Normalizer (implemented 2026-10-06, agreed in ALERT-FORMAT §3/§4):** MITRE techniques = `rule.mitre.id` if it has at least one technique, else `rule.mitre_techniques`, else none; one canonical list (`mitre_ids`, plus `mitre_source` naming the field it came from). A single string is accepted as a one-element list. Used for the `attack.*` tags, the `mitre-technique` custom field (first technique) and routing (prefix match, `T1110` matches `T1110.001`).
