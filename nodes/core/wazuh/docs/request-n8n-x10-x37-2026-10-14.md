## X-10: your conditions accepted; your two questions answered from the source

**Conditions: all three accepted.**
1. Retry on **404** too (n8n starting, or `n8n-import.sh` re-activating). 403 and 422 stay final.
2. **Fast-fail:** once a chain is exhausted, a mark file next to the script (with its time). While it's there, every alert gets one try and no waits. The first success removes it, and so does a re-arm after 5 minutes.
3. n8n deduplicates by alert id at queue insert (your side).

**Already built and tested, held back:** on branch **`wazuh-x10`** on GitHub (only the X-10 changes: https://github.com/poinsot/asox-soc/compare/wazuh...wazuh-x10). It stays outside `wazuh`, so it can't reach `main` before your side is ready. It covers all three conditions.

- Live, n8n restarted during a delivery: the alert arrived on try 4, with one `recv-wazuh-alert` execution.

**One finding you may want for C1's wording:** integratord passes a literal `> /dev/null 2>&1` as the script's last argument (it appends the redirection before splitting the command, and runs it without a shell). The script reads `<timeout>` / `<retries>` as the first two numbers after the URL.

I'll open the pull request after 2026-10-20 together with your N8N-1.9; the C1 check in `contracts-check.sh` is yours (stop n8n, send the test alert, start n8n, expect one execution).

**Q1. Does integratord enforce `<timeout>`?** **No.** In `src/os_integrator/integrator.c` (v4.14.8), `<timeout>` and `<retries>` are only formatted into the script's command line. integratord then starts the script with `wpopenv`, reads its output to the end, and `wpclose` waits for it to exit, with no alarm and no kill (`src/shared/exec_op.c`). So the script alone decides how long a chain lasts; the ~87 s worst case isn't cut short.

**Q2. Alerts still unread in `alerts.json`:**
- **Midnight rotation: none lost.** `jqueue_next` (`src/shared/json-queue.c`) keeps reading the open file to its end. Only when it gets no more data *and* the inode has changed does it reopen the new file, from its **start** (`jqueue_open(queue, 0)`). Alerts written to the old file before the rotation are delivered first.
- **Manager restart: lost.** At start, integratord opens `alerts.json` with `jqueue_open(&jfileq, 1)`, which **seeks to the end**. Alerts written before the restart but not yet delivered are skipped, and so are alerts written while integratord was down. That is true today without retries too; retries only make the backlog longer while n8n is down. **Proposed C1 wording:** "Alerts still queued in the manager when it restarts are not delivered to n8n (they remain in the indexer)."

## X-37: which rules put decoded fields in `rule.description`

Checked in the files on 2026-10-14. **Custom rules:** 27 of 30 interpolate fields; only 100100, 100400 and the retuned 87702 are static. **Built-ins:** 704 of Wazuh's 4,515 rule descriptions interpolate fields. Those the scenarios use are static except 86601 (Suricata) and 19004 / 19007 (SCA).

How far an attacker can steer the text depends on the field:

| Field in the description | Who controls the text | Rules |
|---|---|---|
| `srcip`, `dstip`, `src_ip`, `dest_ip`, `dest_port` | Decoded as an address or a port: an attacker picks *which* address, not free text | 100200, 101000–101002, 101010, 103000, 103010–103012, 108000, 108001, 108010, 108011 |

| **`dstuser`, `srcuser`, `group`** | **Free text from the log line** (a user or group name an attacker can choose) | **100210, 100211, 100212, 103010, 103012** |
| **`file`** | **Free text: a path an attacker can create** | **100300–100303, 108020, 108021** |
| `scenario`, `run_id` | The lab trigger only (rule 100101, level 3, never sent through C1) | 100101 |
| none | — | **static:** 100100, 100400, 87702; built-ins 5712, 5715, 5760, 5763, 5404, 5901, 5902, 40111, 40112, 40501, 2502, 550, 554, 60122, 60204 |

## Grafana's question (Jesus): `new-user` fired 40501, not 5901

**Yes, expected, and correct.** 40501 (built-in, level 15, "Attacks followed by the addition of a user", T1068/T1136/T1203) fires when a user or group is added after **4 or more alerts of group `attacks`** (e.g. 40112) from the same location within 5 minutes. On the dashboard runs, `new-user` came right after other scenarios on the same lab log, so Wazuh correlated the chain. It replaces 5901 or 5902, whichever account event comes first.

- **Run alone,** with no attack alerts in the last 5 minutes, `new-user` gives 5901, 5902 and 100211. That's what `trigger.sh --help` lists.
- **After other scenarios,** expect 40501 in place of 5901 or 5902. `tests/e2e.sh` accepts both, and the catalog lists 40501.
- **At level 15** it reaches n8n on every such run. That's right for a real attack chain. If it's noise on the lab dashboard, filter `rule.id:40501` out of that panel rather than tuning the rule.
