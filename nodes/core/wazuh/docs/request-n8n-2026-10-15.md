## X-38 (Jev): the source address in web access logs

Checked in `wazuh-logtest` (4.14.8) on 2026-10-15 with Apache combined and nginx lines, from a file and over syslog. The cases are now pinned in `tests/cases/builtin-linux.cases`.

- **One decoder for both servers:** **`web-accesslog`** (`decoder.name`), for Apache's combined format and nginx's default formats, whether read from the access log file or received by syslog (`nginx:` program).
- **Fields it decodes:**

  | Field | Value |
  |---|---|
  | `data.srcip` | The first field of the line, the server's `$remote_addr` / `%h` |
  | `data.url` | Path and query string, attacker-written |
  | `data.protocol` | The HTTP method |
  | `data.id` | The HTTP status code |

- **Not decoded:** user agent, referer, and nginx's trailing `$http_x_forwarded_for`. There is **no `data.http_user_agent` or referer field**. They exist only inside `full_log`, as attacker-written text.
- **`data.srcip` is the connection's peer as the server saw it**, and `X-Forwarded-For` never reaches it, with one exception. On a server behind a reverse proxy or load balancer, `$remote_addr` is the proxy's address. If that server rewrites it from the header (nginx `real_ip_header` + `set_real_ip_from`, Apache `mod_remoteip`), `data.srcip` is the header's value again, trustworthy only as far as the trusted-proxy list is strict. That's per web server, not per decoder.
- **Rules that fire on them:** 31100 (grouped, level 0), 31101 (4xx, level 5), 31103 (SQL injection pattern in the URL, level 7), among Wazuh's web rules (`0245-web_rules.xml`).

For `untrusted-fields.json`, `web-accesslog`: `data.url` and `full_log` are untrusted; `data.srcip`, `data.protocol` and `data.id` are decoded values. No 500-character risk except in `data.url` and `full_log`.
