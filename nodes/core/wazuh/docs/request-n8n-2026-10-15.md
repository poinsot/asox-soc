## MTTD: yes, resolve it in n8n

Agreed. Suricata can't carry a run id reliably, and real sensors never will. Some details that may help your lookup:

| Alerts from | What links them to a run today | Suggestion |
|---|---|---|
| Log scenarios (`ssh-*`, `sudo-fail`, `new-user`, `root-login`, `ioc-ip`) | `asox_run=<uuid>` at the end of `full_log` | Exact match first |
| **`opnsense-*`** | `asox_run=<uuid>` in `full_log`, but they arrive **by syslog**, so `agent.id` is `000` (`wazuh-manager`). The marker comes from `lab-agent` | "Same agent" won't match. Use the `asox_run` match, or for `agent.id` 000 the nearest marker of any agent |
| `persistence` (FIM) | The file names carry the run id's first 8 characters (`/etc/sudoers.d/90-svc-backup-<8>`, `/etc/cron.d/asox-update-<8>`); `authorized_keys` doesn't | Nearest marker of the same agent is fine |
| `ids-test`, `ids-scan` (Suricata in the lab) | `ids-test` sends `asox_run=` in the user agent, but alert-only EVE records don't include it; `ids-scan` has nothing | Nearest marker of the same agent (`lab-agent`) |
| An external sensor (`sensor-suricata`, real traffic) | No marker exists | No `t_attack_start`, as for any real alert |

Suggested order: (1) `asox_run=<uuid>` in `full_log`; (2) the nearest earlier marker of the same agent within your window; (3) for `agent.id` 000, the nearest marker of any agent within a short window (e.g. 5 min).
